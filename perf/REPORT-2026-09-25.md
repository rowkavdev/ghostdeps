# Worker production profiling baseline — 2026-09-25

The 4 GiB worker sizing was ceiling math: 512 MiB heap per adapter worker x
max 4 parallel workers per job x queue concurrency 2. Nobody had measured the
worker under real load. This baseline measures the production pipeline end to
end — codeload tarball download, `extractTarball`, `FsRepositoryHandle` scan,
`analyseRepositoryIsolated` with the app's four default adapter modules — on
the pinned regression corpus (vite, fastify, uuid, chalk, nanoid, got) plus
one real repo per non-JS adapter (bat, flask, cobra) and three large JS
codebases (babel, TypeScript, next.js) to find where the budgets bind.

Everything below is reproducible with `node perf/profile-worker.mjs`; raw
measurements are in `perf/results/baseline-2026-09-25.json`. Methodology and
caveats are at the bottom.

## Finding 1 — memory: the ceilings have ample headroom, measured

The worst single job measured (next.js, 4,718 direct dependencies) peaked at
464 MiB for the _whole process_ — main thread, engine, and all four adapter
workers. No adapter worker came close to its 512 MiB heap ceiling; the entire
job stayed under one worker's allowance. The production-shaped worst case —
two heaviest jobs in one process, the queue-concurrency-2 shape — peaked at
627-661 MiB over three runs (next.js + TypeScript), i.e. ~16% of the 4 GiB
box. Single-job headroom vs the 4 GiB sizing is ~9x; measured two-job worst
case is ~6x.

Corollary: on a 4 GiB box, memory is not the binding resource at concurrency 2. Higher concurrency (3-4) is a ceiling-estimate hypothesis, not a
measurement: 0.66 GiB measured for the worst pair scales to roughly
1.0-1.3 GiB for 3-4 concurrent next.js-scale jobs, which still fits — but
the real limit would be CPU (see Finding 2), so concurrency should be matched
to cores, not gigabytes. Untested here: production core count and any
concurrency above 2.

## Finding 2 — the 60 s adapter stage budget binds on usage analysis at next.js scale

The per-stage timeout (DEFAULT_ADAPTER_TIMEOUT_MS = 60 s, one budget per
stage per adapter worker) is the only compute budget that comes close to
binding. Per-stage wall times for the JavaScript adapter:

| repo    | detect | dep listing | dep graph | usage analysis (budget 60 s) |  notes |
| ------- | -----: | ----------: | --------: | ---------------------------: | -----: |
| chalk   |   6 ms |        1 ms |      5 ms |            0.12 s (11 calls) |   1 ms |
| nanoid  |   6 ms |        2 ms |     98 ms |            0.22 s (20 calls) |   1 ms |
| uuid    |  22 ms |       11 ms |    189 ms |            0.41 s (35 calls) |   9 ms |
| got     |   4 ms |        2 ms |     10 ms |             1.1 s (50 calls) |   3 ms |
| fastify |  10 ms |        6 ms |     60 ms |             1.3 s (53 calls) |   2 ms |
| vite    | 386 ms |      160 ms |     1.3 s |            3.8 s (484 calls) | 153 ms |
| next.js |  1.0 s |      331 ms |    17.8 s |    **~60.0 s (2,398 calls)** |      — |

next.js usage analysis lands at ~100% of the 60 s stage budget. In the
solo isolated run it completed (13,278 usages recorded, analysis 62.5 s
total), with essentially no margin. **Under production-shaped concurrency it
tips over**: in both instrumented next.js + TypeScript runs (queue
concurrency 2 on 2 cores), the next.js job posted `javascript-typescript
analysis incomplete: usage analysis timed out` — the in-worker stage timeout
firing under the second job's CPU contention.

One anomaly needs a core follow-up: those same two runs still recorded all
13,278 usages alongside the timeout finding, while the stage error path in
run-adapter.ts leaves `outcome.usages` empty on a timeout. Either the
in-worker timeout raced a just-completing stage, or partial state survives
somewhere the code reading does not predict. The conservative reading is
that the intended failure mode is quiet loss of all usage facts (one info
finding, no usage data for 4,718 dependencies, no verdicts); the observed
behaviour at the boundary should be pinned down before relying on either
outcome. Follow-up issue recommended.

Usage analysis is also ~75-85% of stage time on every repo measured, and the
graph + usage stages run concurrently (run-adapter.ts `Promise.all`), so the
usage stage is the long pole outright. Recommended fixes, in order:

1. Scale the usage-stage budget with the dependency count (e.g.
   `max(60s, 30ms x deps)`), or give the usage stage its own larger budget
   (5 min). A flat 60 s is calibrated for repos 20x smaller than next.js.
2. Salvage partial usage results on timeout: today a timeout discards even
   completed per-dependency results. Keeping them as _facts_ with
   `usageAnalysed: false` (which already blocks verdicts) preserves most of
   the value for large repos without weakening the no-false-unused rule.
3. Non-JS adapters measured far from the budget (rust 0.61 s, python 0.18 s,
   go 0.11 s usage stages on real repos), so this is a JS-adapter-sized
   problem today.

## Finding 3 — the scanner's 50k-file cap binds on TypeScript-scale repos

TypeScript's tarball extracts to 66,672 files; the scan stops at
`maxFiles: 50,000` and the run is marked `scanIncomplete`, which blocks
"unused" verdicts repo-wide (conservative and correct, but the repo gets
facts only). The scan itself is cheap (3.3 s, 145 MiB listed) and memory is
fine, so the cap — not the hardware — is the limit. Options: raise
`maxFiles` for the app worker (100k keeps scan time ~7 s at measured rates),
or accept facts-only for mega-repos and document it. Worth checking how many
installed repos actually exceed 50k files before spending on this.

## Finding 4 — tarball download/extraction is file-count-bound, far from caps

Worst compressed tarball: 49.3 MiB (next.js) against the 512 MiB cap (10x
headroom). Worst download+extract: 21.4 s for TypeScript's 66,672 files
against the 5-minute download timeout (14x headroom) — and that number is
dominated by creating tens of thousands of small files, not by bytes (babel:
10.0 s for a 7 MiB tarball). Note for provisioning, not for budgets:
extracted checkouts are large on disk (TypeScript ~150+ MiB), and each job
uses its own mkdtemp, so /tmp sizing on the worker host matters more than
the memory ceilings.

## Finding 5 — footprint budgets bind immediately when enabled (currently env-gated off)

`GHOSTDEPS_FOOTPRINT` is off by default; measured with
`NpmMetadataService` wired in:

- **uuid** (committed package-lock): 820 package versions requested, 300-
  fetch per-run budget cut in, 292 sized, `complete: false`. Under the #313
  rule a truncated footprint is never cached, so every re-run of that SHA
  re-pays the provider cost (~3.3 s, pushing the job from ~1.4 s to ~4.5 s).
- **nanoid** (pnpm): 134 versions requested, **0 sized** — the public-origin
  allowlist skipped every pnpm-lock origin. pnpm repos get no footprints.
- **vite, fastify, got, chalk**: 0 provider calls at all — footprints only
  attach to impact entries with a known closure, and committed-lockfile
  coverage decides everything.

Before enabling the flag: raise the fetch budget or prioritise direct
dependencies, and check pnpm lockfile origins against
`PUBLIC_NPM_REGISTRY_ORIGINS`.

## Not load-tested here

- Queue behaviour under webhook floods (maxPending 500, dedupe window 1000,
  supersede-on-push) — needs a delivery-driven test, not a repo scan.
- The result cache (16 MiB, 4 entries/repo) under real hit rates.
- PR-scoped jobs (diff parsing, dependency-change extraction) — this
  baseline measured full-scan jobs only; PR jobs are strictly cheaper on the
  analysis side but add the diff fetch.

## Methodology and caveats

- Harness: `perf/profile-worker.mjs`, one hermetic child process per measured
  run (peak RSS is per-run clean), 25 ms memory sampling plus VmHWM/getrusage
  cross-checks, per-stage timing via busy-wall measurement (usage calls run
  8-wide, so naive per-call sums overcount ~8x).
- The pipeline measured is the worker's real path: same tarball streaming,
  extraction, scan, isolation tier, adapter modules, and default options
  (recommendations on, footprint off except in footprint runs).
- Measurement box: 2 vCPU / 2 GiB sandbox — smaller than the production
  sizing. Absolute times will drop on bigger hardware; the binding _ratios_
  (Finding 2's ~100%, Finding 3's 1.33x over cap) are the durable signal.
  Memory peaks are allocation-driven and transfer across hardware.
- next.js timing evidence: one solo isolated run, one in-process staged run
  (both land the usage stage at 59-60 s), and three next.js + TypeScript
  concurrent runs, two of them instrumented for finding kinds. The timeout
  finding fired in both instrumented concurrent runs. Treat the exact solo
  margin as noise; treat "no headroom, and over the edge under concurrency"
  as the finding.
- Repos pinned by full SHA (`corpus/repos.json`, `perf/corpus-extra.json`),
  measured 2026-09-25 against ghostdeps @ cb30c3f (plus this harness).
