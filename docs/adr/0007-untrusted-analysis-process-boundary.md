# ADR 0007: Process boundary for untrusted static analysis

- Status: Proposed
- Date: 2026-09-27
- Scope: #326. This records the target boundary, **not a deployed security control**.

## Problem and current state

Repository-controlled archives, filenames, source, manifests and lockfiles reach parsers in Node worker threads. A worker's `resourceLimits.maxOldGenerationSizeMb` does not cap WASM, native allocations or the parent process. Workers share the App process, its network namespace and its ability to mint installation tokens. The offline `AdapterContext` policy is cooperative, not a firewall. No repository code is intentionally executed, but parser compromise is in scope. The present checks are useful bounds, not credential, filesystem or egress isolation (see ADR 0004 and `docs/security-model.md`).

## Proposed trust boundary

Split the service into a **privileged broker/reporter** and an **unprivileged, disposable analysis process**. The broker owns the App private key, token minting, authenticated GitHub requests, tarball fetch, PR diff fetch, optional public npm metadata, check-run reporting and cache. It validates and extracts the tarball into a fresh per-job workspace before launch; never let a hostile archive choose a path or module specifier. The child only sees one read-only checkout, immutable bounded analysis parameters, and a writable scratch directory. It returns findings as data. No App key, installation token, credential-bearing environment variable, host socket, or broker filesystem is mounted or inherited. The child does not make authenticated or registry requests. Static parsing only; this ADR does not approve executing repository scripts, installs or build tooling, including in a container. The local CLI retains its current offline worker-thread mode until an explicit local opt-in is designed; it must not claim the App's process boundary.

The target production runner is a per-job, rootless container (or an equivalently verified OS sandbox) launched by a dedicated runner, **not Docker socket access from the App service**. A separate runner/pod control plane should receive a bounded job descriptor and an immutable checkout artifact from the broker. Its daemon/socket is privileged and must not be exposed to either the App's parser or the analysis child. A plain `child_process`, worker thread, restricted JS globals, or `NetworkPolicy.offline` does not meet this boundary. If the chosen deployment cannot enforce all properties below, fail closed to a bounded neutral check; do not silently fall back to in-process analysis for untrusted jobs.

## Child contract and limits

- **Input:** versioned descriptor with job ID, analysis options, allowlisted built-in adapter IDs and checkout digest. Reject unknown fields, paths and adapters; never import adapter code from the checkout. Checkout is mounted read-only, with no symlinks materialised by extraction. Give the child no host path outside the checkout and its private scratch. Avoid `--privileged`, host namespaces, host PID, host mounts and ambient capabilities. Drop capabilities, use a non-root UID, `no-new-privileges`, a read-only root filesystem and a syscall policy. Set scratch to an ephemeral bounded filesystem. Mount no service secrets, credentials, Unix sockets, service-account tokens, or cloud metadata endpoints.
- **Egress:** deny all outbound network at the container/namespace policy, including DNS, loopback access to host services, IPv4/IPv6 and cloud metadata. Registry metadata stays broker-side with its existing public-origin rules. If a future adapter needs network, define a separate narrow broker capability and review it first; no general network exception in this child.
- **Resources:** bound the _entire child cgroup_, not only V8: initial cap 3 GiB total memory (JS + WASM + native + page cache), 2 CPU cores, 256 MiB scratch and at most 128 processes/threads; at most one child per analysis job and two concurrent jobs per service. Keep the existing 512 MiB per-adapter V8 old-generation heap and at most four adapter threads within that cgroup, but treat the cgroup cap as authoritative. Existing 512 MiB compressed, 1 GiB extracted and 200,000-entry tarball ceilings still apply before launch. Budget the broker's extraction and cache separately from the child, set a host-level service memory ceiling, and benchmark worst-case Rust/WASM fixtures before production. Proposed values are deployment targets to validate, not proven safe defaults.
- **Time:** keep the existing 5-minute download/extraction timeout. Set an explicit child wall clock deadline (initial target 10 minutes, including startup and teardown), plus cgroup CPU quota. On deadline, OOM, signal, malformed output or lost runner, terminate the entire process group/container, reap it, remove the workspace, and complete the check neutrally. No unbounded wait for a blocked child or reporter. Log an error category, not raw attacker-controlled output.
- **Output:** one versioned, length-prefixed structured result, with an enforced byte ceiling _before_ parsing or copying into broker memory (initial target 16 MiB). Stream from a bounded pipe/file, reject extra frames, unknown schema, non-finite numbers and invalid lengths. Bound strings, arrays, evidence and finding counts before the check renderer; existing `OUTCOME_CAPS` after a worker structured-clone do not protect the parent heap. Treat all child text as untrusted display data and never as instructions or a privileged API request. No channel from child to token broker or GitHub reporter except this one-way result. If output exceeds the cap, emit a neutral limitation, never a partial high-confidence "unused" verdict.

## Failure semantics and rollout

The broker creates an in-progress check and guarantees a bounded neutral completion on child failure, invalid output or timeout; it must not call an untrusted child to render failure text. `CheckReporter.fail` already gives a neutral result for ordinary errors, but watchdog and process teardown need tests so the promise holds when a child hangs or OOMs. A broker/API outage may still prevent posting a check; alert and retry that separately rather than claim a check was completed. Do not cache failed or partial results or post a remediation comment from them. Keep the current thread mode explicitly labelled as non-OS-isolated until a production deployment passes adversarial tests and an independent reviewer verifies the actual runner/container configuration.

Implementation slices: (1) broker/child protocol and strict bounded validation with injectable runner; (2) runner with OS isolation and malicious-adapter tests for network, key, token, host files, oversized output, OOM and teardown; (3) integration/e2e tests covering oversized tarballs and parser failure; (4) deployment validation, metric dashboards and feature gate. No feature gate flips just because the code merges. Record isolation mode and runner version in diagnostics, with counts for child exit reason, deadline/OOM, output rejection, cleanup failure, neutral checks, queue time and memory peak. Deployment docs must pin the container runtime, namespace/network policy and CI verification commands. If isolation cannot be verified, remain in the existing mode with an explicit risk note only in development; production cannot present it as isolated.

## Alternatives

Worker threads alone: rejected for secret, native-memory and network isolation. A bare process with an empty environment: rejected for shared host filesystem/network access. Running an OCI container through a Docker socket mounted into the App: rejected because compromising the App can control the host runner. Granting registry egress to the child: rejected; the broker already has a bounded metadata path. A silent fallback to thread mode: rejected because an outage would downgrade a security guarantee.

## Open validation before acceptance

Choose a concrete runner and deployment host, measure parser peak memory and result sizes on the adversarial corpus, and agree on the operational limits above. Review the PR-comment fix-preview/revalidation path too: it currently reopens the checkout in the broker after scanning, so it must move behind the same boundary before this feature is enabled. This ADR is proposed until those choices and tests are reviewed; it does not assert that an OS boundary exists today.
