# ADR 0005: Fix proposals and isolated verification

- Status: Proposed (lead review required)
- Date: 2026-09-25
- Scope: M4 design for `ghostdeps fix`; no implementation is authorised by this document

## Context

GhostDeps currently produces evidence-backed findings, not edits. The CLI has no `fix` command yet. The GitHub App has read-only repository permissions plus Checks write; it cannot push a branch or open a remediation PR. The existing engine and adapters analyse a read-only `RepositoryHandle` (ADR 0002), and ADR 0004 forbids running repository code in analysis. A plausible-looking edit is not proof that it preserves behaviour, and an install or test command in the App worker would expose the service and its credentials to untrusted code.

M4 should let someone inspect a proposed change without implying that every finding can be fixed automatically. The newer human-in-the-loop [PR comment and tick-to-apply design](../pr-comment-apply-design.md) owns App delivery after an eligible proposal is generated; this ADR owns what can be proposed, not that App workflow. A finding's confidence is an analysis claim, not a certificate that its edit is safe. In particular, a partial scan, absent lockfile, unknown package-manager settings or ambiguous dynamic usage must not turn into an automatic removal.

## Decision proposed

**Generate a bounded, reviewable patch from a supported finding and verify it in separate stages. Never apply or merge it automatically.** The first release is an explicit, dry-run CLI proposal. App delivery and same-PR commits require the separate, opt-in workflow in the [PR comment and tick-to-apply design](../pr-comment-apply-design.md). M4 implementation waits until M3 is stable, this ADR and the isolation design are accepted, and the security gates below have tests. The proposal remains inert when the requirements are not met.

A candidate has these states: `not-supported`, `blocked`, `generated`, `statically-checked`, `sandbox-verified`, `verification-failed`, `verification-unavailable`, `stale`. Only `sandbox-verified` means the configured commands completed in a sandbox; it does **not** mean behavioural equivalence. A static check alone must not be labelled verified. Show the verification scope and limitations beside the patch on every surface. Never infer the state from a check run's overall success or a finding's severity.

### Eligibility and finding-specific edits

The candidate is bound to the exact repository snapshot, ecosystem, project root, manifest path, package manager and dependency declaration (name, kind and constraint), plus a rule id and evidence digest. The engine first requires a successful, complete scan of the relevant ecosystem and declaration, an unambiguous project and supported manifest syntax. Incomplete coverage or unresolved references block a fix even when the current reporter still displays a finding. `unused` is currently capped at medium confidence pending corpus validation; do not treat a medium cap as proof that a removal is safe. A dedicated fix eligibility check must require the underlying rule's prerequisites and independent fix-safety guards, not merely `kind === "unused"` or confidence text. If that underlying proof is not available in the current result, add it to a named internal `FixEligibilityEvidence` input rather than reverse-engineering a verdict from a display cap.

Do not guess which manifest to edit from a package name shared across workspaces. A finding without a unique project/declaration key stays informational until core can bind it. Python executable manifests (`setup.py`) and unsupported syntax are never evaluated to discover an edit location. Package manager lockfile changes are allowed only through a deterministic, data-only, tested writer for the exact supported format and version. Preserve unrelated entries and formatting where possible; reject unknown schema, stale lockfile, resolution changes requiring network or execution, or a manifest/lockfile pair that cannot be shown consistent. Do not hand-wave a lockfile as correct because a textual package name disappeared. Initially, it is acceptable to support a narrow format or return `not-supported`; never silently leave a lockfile stale. Go, Cargo and Python scopes and lockfiles get ecosystem-specific recipes and tests before eligibility is advertised. Do not present a supported manifest-only fix where the package manager requires a lockfile update.

### Contract and data flow

Keep the existing `analyseRepository` path read-only. The core owns selection, eligibility policy, diff assembly, verification status and final result. Adapters supply **facts and optional edit recipes**, never policy or host filesystem writes. Extend `AdapterCapability` with a versioned `fixGeneration` capability and an optional method that receives a bounded, immutable proposal context: the eligible finding, exact `Dependency` and project, usages and limitations, repository snapshot/read-only handle, plus the edit intent chosen by core. Return declarative edits (`path`, exact expected content hash or anchored range, replacement bytes, recipe id/version, rationale), or a structured unsupported reason. An adapter cannot supply a shell command, grant network access or claim a fix verified. The core validates the returned edits independently before rendering or applying anything; capability absent means `not-supported`. Changing required method semantics or trust boundaries requires an adapter API version bump and contract tests (ADR 0002). Additive fields follow the existing version policy only when old adapters remain valid.

The core reads each target file from the pinned snapshot, verifies hashes and expected spans, rejects overlapping edits, duplicate paths, unsafe path components, symlinks, hardlink aliases, binary or generated files, disallowed encodings, oversized files and out-of-project targets. Every final byte is assembled once in a bounded in-memory overlay. No adapter gets a writable repository or direct network access. Reanalyse that overlay statically through the same engine and compare scoped facts: target declaration changed as intended; the finding has not merely disappeared because the adapter failed, timed out or lost coverage; unrelated declarations and files did not change. A failed or incomplete reanalysis blocks the candidate. Note that absence of a finding alone is not a pass.

`FixEligibilityEvidence` should be a core-owned, versioned, immutable record of the rule prerequisites (coverage flags, reference-analysis completeness, exception/allowlist checks, matched project and declaration identity, scan limitations, and source snapshot digest), with explicit unavailable values. It is not an open-ended adapter bag or a user-facing claim of safety; core validates its provenance before an edit can be eligible. Its precise fields and contract tests are part of implementation review.

Suggested core API shape (illustrative, not a committed signature): `proposeFix(handle, analysis, findingRef, options): FixProposalResult`. `findingRef` includes rule, ecosystem, project, manifest, dependency and source snapshot hash, rather than using the array index or package name alone. `FixProposalResult` carries a version, before/after SHA-256 hashes for every edited file, bounded edits and a unified diff, baseline/overlay analysis summaries, recipe version, status and limitations. Do not silently append a generated patch to `AnalysisResult` schema v1; expose it as a separate versioned artifact, and only add optional report fields if deliberately specified and tested. Serialize and sort deterministically, escape repository-controlled text as in the current JSON reporter. A missing or malformed adapter response is a blocked proposal, not an empty patch.

The CLI should expose `ghostdeps fix <pkg> [path]` as an explicit preview command, with a project selector when names collide. It prints exact paths, diff, reasons for any block and the verification state. Default is no write. A separate explicit local apply operation, if implemented, rechecks file hashes and repository state immediately before writing, writes atomically, and does not commit. A human can inspect and run their own tests. The App's human-in-the-loop delivery is specified in the [PR comment and tick-to-apply design](../pr-comment-apply-design.md): it renders one maintained comment and delegates head-pinned, maintainer-triggered manifest and lockfile edits to a trusted Action on the repository runner. The App does not directly mutate PR branches or run package managers. This replaces the earlier separate remediation-PR delivery shape for this feature; a future separate-PR mode requires its own decision. No check annotation or comment should say "fixed" before the validated edit is committed.

### Isolation and verification

There are two distinct stages:

1. **Static and structural verification** is mandatory and executes no target-repository code. Validate edit boundaries and lockfile consistency with parsers, then run the existing engine over the candidate overlay. This is all that may run under today's ADR 0004 policy. A failure or partial scan blocks the patch; lack of a supported verifier is `verification-unavailable`, never a pass.
2. **Dynamic verification** (install, compile, test or tool invocation) is conditional future work. ADR 0004 explicitly bars executing repository code in the service and requires a defined isolation tier and a separate decision before tooling runs. Accept or amend that policy explicitly in security review before enabling this stage. A container name or `--ignore-scripts` alone is not a security boundary. Until then, present generated proposals as statically checked, not sandbox-verified; do not secretly run commands on a developer's local checkout either.

For the proposed isolation tier, a privileged orchestrator outside the analysis worker creates one fresh, disposable sandbox per candidate using an immutable image and pinned toolchain. It receives only a validated copy of the pinned snapshot plus patch, never `.git`, host mounts, SSH agents, cloud metadata, service environment or tokens. The service and App credentials remain outside the sandbox; no Docker socket or nested container runtime is mounted. Root filesystem read-only, unprivileged uid, no ambient or added capabilities, no privilege escalation, restrictive seccomp and namespace isolation, cgroup CPU/RAM/process limits, disk/file-count quotas, wall-clock deadlines, and a single writable ephemeral work area; destroy it on every exit, timeout or crash. Prefer stronger host isolation (microVM or equivalent) if the container runtime cannot enforce these controls against hostile build tools. Treat the isolation technology, escape threat model and enforcement tests as a release gate, not an implementation detail.

Default network is **off** including DNS. Offline dependency resolution must use a preloaded, immutable, content-addressed cache or fail unavailable; never map a host package cache writable and never mount user credentials. If an ecosystem cannot install or build without network or lifecycle scripts, it is not dynamically verified in this tier. Any future network-enabled verification needs a separate security decision with an exact destination allowlist, no repository data or private package name leakage, and credentials scoped outside the execution environment. `--ignore-scripts`-style flags are defence in depth, not a licence to run untrusted code. A configured test/build command is itself repository-controlled code and is only eligible after the isolation policy is approved; commands must come from a reviewed allowlist, not an adapter string, repo README or arbitrary manifest field. Tests are optional signals: some projects have no runnable test suite, and a green suite does not prove semantic equivalence.

The verifier records image digest, tool versions, snapshot and patch hashes, command list, exit codes, timeouts and bounded, redacted logs. Reject attempts to exceed budgets; a crash, skipped command, unavailable dependency, unexpected network need, or incomplete results never becomes green. Truncate logs before display, strip terminal controls and secrets, and retain them briefly under access control. Dynamic verification rechecks the exact patched bytes it received; a successful run cannot be reused for a different head, patch or toolchain. Sandboxed output is untrusted data and cannot add instructions, edits or permissions.

### Presentation and ownership

Show a unified diff with file headers, context and line counts, plus a short change summary, precise dependency/project identity, evidence and limitations, and a verification table (`static`, `lockfile`, optional `sandbox`) with `passed`, `failed`, `unavailable` or `not-run`. Bound diff bytes and files. If a diff exceeds the presentation cap, return a blocked or clearly incomplete preview rather than silently dropping hunks while offering an apply button. Escape ANSI, bidi and control characters; never render repository text as HTML. Show changes to lockfiles explicitly. CLI users choose whether to apply a local patch; App users explicitly tick eligible items in the maintained PR comment under the linked delivery design. GhostDeps does not auto-merge, auto-close an issue, or interpret a green CI check as consent.

For the opt-in tick-to-apply flow, re-check the PR head and finding evidence immediately before dispatch and again on the runner before writing. Constrain edits to the PR branch, protect against duplicate webhook deliveries and never push a stale or manifest-only lockfile-bearing change. Fork PRs need the explicit allow-edits and write-capability gates in the delivery design. Unavailable permission, workflow or changed heads degrade to diff-only or a refusal. The normal repository's CI and review still decide whether to merge. Never request broad App write permission as part of an ordinary scan install without explicit opt-in.

## Rejected alternatives

- **Auto-apply every `unused` verdict:** incomplete analysis and cap-lowered confidence make destructive edits too easy; finding confidence and fix eligibility are separate.
- **Have adapters write files or run package managers:** breaks the read-only contract and lets untrusted inputs choose side effects.
- **Run `npm install --ignore-scripts` or tests in the App worker:** forbidden by ADR 0004, with unacceptable token and host exposure.
- **Produce manifest-only edits for every package manager:** a stale lockfile is a plausible-but-wrong patch.
- **Open or merge a remediation PR on a green sandbox run:** tests do not establish correctness or replace the maintainer's review. The newer tick-to-apply design changes the existing PR only after a maintainer tick and fresh eligibility check.

## Rollout and acceptance tests

1. Stabilise M3, accept the ADR and resolve ADR 0004's execution policy. First release a dry-run, static-only JavaScript/TypeScript `package.json` + npm `package-lock.json` recipe (the deepest current evidence base, with a pinned corpus check), with a fail-closed unsupported result for all other formats.
2. Contract fixtures for each supported rule and package manager: multiline and duplicate declarations, monorepos, name collisions, non-registry specs, malformed manifests and lockfiles, scripts/config/dynamic use, missing runtime floor, stale snapshot, renamed paths and an unchanged unrelated file. Assert exact bytes, hashes, diff, deterministic output and no write on preview.
3. Adversarial fixtures: traversal, symlink and hardlink targets, control characters, huge files and diffs, adapter crashes/timeouts/malformed edits, overlay scan failure, network attempt, secret access, resource exhaustion and verifier logs containing instructions. Each must block or degrade, never report success.
4. Before dynamic verification, security review the precise isolation implementation and prove network/token isolation and cleanup with executable tests. Ship disabled by default, observe failures and use an explicit opt-in. App tick-to-apply is a later permission-gated slice under the linked delivery design; test maintainer authorisation, head-pinned same-PR writes and stale-head rejection. No implementation lands as a single broad drop.

## Consequences

The fix feature will say "cannot propose a safe edit" often at first. That is intentional. The boundary is a reviewable patch, not a claim that the dependency can always be removed or that running tests proves safety. Core and adapters retain their existing analysis roles; the new writer and verifier live behind a separately gated proposal path.
