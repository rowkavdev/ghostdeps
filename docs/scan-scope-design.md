# Scan scope design (#354)

- Status: Accepted design (lead ruling 2026-09-25); implementation authorised 2026-09-26 (lead ruling; first slice in #422)
- Date: 2026-09-25
- Driving case: GhostDeps's own fixture manifests produce noisy but correct self-scan findings

A scan result describes the files GhostDeps was allowed to inspect. If a user narrows that set, the result must say so in the ordinary CLI output and GitHub Check, including when no dependency findings remain. A clean-looking result with hidden declarations is worse than the fixture noise this proposal addresses.

This design draws on the research memo for [#354](#evidence-and-alternatives), the existing [scanner contract](repository-scanner.md), [ADR 0004](adr/0004-analysis-sandboxing.md), and the [result guide](interpreting-results.md). It does not change today's built-in vendor/generated exclusions, recommend a stopgap `fixtures/` filter, or treat excluded files as already analysed.

## Smallest useful scope

**V1 mechanism (lead ruling 2026-09-25):** explicit, repository-relative **fixture roots**, not a general ignore language. A config lists exact directory roots (for example `fixtures/`), with no wildcards, negation, file-level excludes or dependency-name suppression. The scanner recognises each root as a declared fixture-only subtree and omits it from dependency analysis. This is a per-repository declaration, not an automatic convention that silently treats every directory named `fixtures` or `test` as a fixture. The App reads a committed repo-root `.ghostdeps.json` at the analysed ref. Explicit per-run CLI/Action input overrides that file for the run; both the override and its provenance appear in the effective scope record. No configuration is implemented today.

Why exact roots: the present problem is a whole fixture tree of fake projects, not a need to hide scattered imports. A short list of literal roots is easier to review, match and audit than `.gitignore` syntax. The scanner already excludes known vendor/generated directories by default, but that list does not make the user's fixture tree disposable. A name-only per-ecosystem convention, such as always ignoring `fixtures/`, would silently miss a real workspace of that name and violate the explicit-scope requirement. A name convention may help suggest a config value, but never activates it without the owner choosing it.

The first slice cannot exclude one source file, one manifest, a package name, or an arbitrary pattern. Those may be considered if real use cases survive this narrower mechanism. They require a separate semantics review, because omitting source while keeping declarations can create false `unused` evidence, and hiding a single manifest changes the project tree without hiding its source. Do not represent future pattern syntax as supported by this proposal.

### Config source and precedence (lead ruling 2026-09-25)

Use one committed, schema-versioned file at repository root: `.ghostdeps.json`. For v1 it contains scan scope only, with exact fixture-directory roots. The precise JSON field names and version value are an implementation decision, but unknown schema versions or unexpected fields must fail visibly, not be interpreted as permissive scope. The committed file is versioned with the code it scopes and can be retrieved at a historical SHA. An App scan reads it from the analysed ref, not from a mutable default branch or process-wide environment.

An explicit per-run CLI or Action input overrides the committed file's scope for that run rather than silently merging lists; the record includes the source (`repo-config` or `per-run-override`), configured roots, schema version and effective-scope digest. A present override of an empty list intentionally clears committed roots and must remain visible as an override. Define the Action input transport and CLI flag syntax in their implementation slice; neither exists yet. The App has no hidden environment override for repo scope. If the committed file is malformed, unsupported or unreadable, a CLI/Action override must not silently launder that failure into a clean result: report the file error alongside the override and mark the run incomplete (or fail the scan). This preserves audit of the versioned declaration. The source and override are bound to the analysed head/SHA.

### Input and matching rules

- Canonicalize paths relative to the repository root using `/`; a root matches itself and descendants on a component boundary (`fixtures/` matches `fixtures/a`, not `fixtures-old/a`). No expansion against the host filesystem, globbing, case-folding, implicit `.gitignore`, environment substitution or network lookup. Root `.` and repository root cannot be excluded.
- Accept only canonically valid directory roots; existence in the snapshot determines matched vs unmatched status, not validity (arbiter reconciliation 2026-09-26: an unmatched root is not a config error - it is shown literally as unmatched with zero counts in the scope block, hides nothing, and never fails the run or marks it incomplete). Reject absolute paths, `..`, backslashes, control/bidi characters, symlinks, non-UTF-8 names and paths that cross the checkout boundary. Reject duplicate or overlapping roots or normalize them with an explicit warning; the first slice should reject so one path has one reason. Bound root length, number of roots and total config bytes. Invalid config is an error or an incomplete run, never a silently ignored entry.
- Identify the config's source, version and hash in the result, and bind the effective scope to the analysed commit/SHA. A config change invalidates same-SHA caches and re-runs. If a repository-controlled config claims to turn off visibility, ignore that claim: reporting rules are code-owned.
- The shared scanner/handle owns the filter before adapter detection. Detection, manifests, lockfile graphs, usage and project-tree assembly must all receive the same filtered view; no presenter post-filter or rule suppression. The existing read-only handle still refuses excluded paths. An adapter cannot override scope by reading from the host filesystem.

**No general pattern language in v1 (lead ruling 2026-09-25).** A broader grammar needs real use cases and its own reviewed slice spelling out ordering, negation, parent traversal and disclosure. Gitignore compatibility must never be implied merely by calling future rules "patterns". The visibility and declaration-gap rules below also constrain any future slice.

## Visibility is the contract

Every run carries an explicit `scanScope` summary in its versioned result, including a zero-match configuration: configured fixture roots, config and override provenance, schema version and effective-scope hash, matched root count, exact matched-file and matched-manifest counts, per-root counts, and whether counting was complete. The count is about paths actually omitted from this snapshot, not the number of configured rules. Count a directory match once as a root, but count files and recognised manifests beneath it by a bounded metadata walk; never present "1 excluded path" as if one file was hidden. Empty directories can match with zero files. Unmatched roots are shown as unmatched, not silently accepted. If the walk cannot determine exact counts because of scan ceilings or unreadable entries, show `unknown`/`at least`, mark scope counting incomplete and make the run incomplete; never print a deceptively exact zero.

The CLI human report and the GitHub Check both show a **Scan scope** block on every run, even with no exclusions configured. With a configured but unmatched root, show its literal name and zero matched files. With a match, add a visible run-level line: "Scanned with exclusions: fixtures/ (N files, M recognised manifests excluded)." List per-root counts under it. The title and finding-free conclusion cannot be the ordinary unqualified quiet-success copy when a matched root excluded declarations; see the declaration-gap rule below. CLI JSON and any Action summary/check carry the same core-owned scope record. `--severity`, `--fail-on` and the check's collapsed sections must not hide it. In a PR check, identify the analysed head and config digest so a reviewer can tell which scope the result covers.

Config text and matching paths are untrusted. Validate and cap them before use, escape terminal controls and Markdown/HTML in every presenter, and never interpolate them as links, commands or trusted formatting. Cap displayed entries and examples, but keep total counts; print a `+N more` disclosure, not an omitted list with an innocent-looking zero. If even the aggregate cannot be represented or the config exceeds bounds, fail closed with a visible incomplete result. The JSON contract distinguishes configured, matched, and unknown counts so consumers cannot infer clean absence from a missing field. The scope summary is not a `Finding` that can be removed by a policy flag or severity filter.

The current default vendor/generated exclusions are a distinct scanner policy. The scope block should identify that built-in policy separately (version or stable identifier, and matched directory/file counts where measured), rather than claiming "no exclusions" while the scanner skips `vendor/` or `dist/`. The first slice may report aggregate built-in counts without listing every built-in directory, but must state that defaults apply and link to their definition. A new user-configured exclusion must never be laundered into the default policy. Changes to built-in skip visibility should be specified and tested alongside the new result schema.

## Declaration and reference completeness

An excluded recognised manifest means GhostDeps cannot know that project's direct dependency declarations. Emit a core-owned `info` **incomplete-family** note with the excluded manifest count and bounded paths, linked to the scope summary. No project detection or policy rule may convert that missing project to "no dependencies" or "no findings". A run with any excluded manifest is **always neutral** in the GitHub Check, even if all analysed projects have no verdicts (lead ruling 2026-09-25). The CLI's result must say declarations were omitted. A fixture path may be intentional, but intent does not turn omitted declarations into evidence of absence.

For all user-configured exclusions that can hide source, decide reference completeness independently from declaration completeness. The safe first-slice policy is a run-wide `scanIncomplete` cap for absence-based verdicts whenever any fixture-root files are omitted: do not assert `unused` from the reduced source corpus. Retain positive evidence from the included projects, marked with the scope limitation. This is deliberately blunt. An eventual project-aware cap could recover precision only if core proves the omitted subtree cannot contain a reference relevant to each remaining declaration. A package name overlap, workspace link, build script, config file or cross-project reference defeats a naive "different directory" proof. Counts and footprint for omitted projects are unknown, not zero; graph completeness for included projects is reported separately. A root with no files need not cap reference analysis but must still be visible as configured.

If configured fixture roots remove all manifests, the output is incomplete, not quiet success. If an excluded root contains malformed or unreadable manifest candidates, count what is knowable from names; note unknown declarations and count uncertainty. Do not suppress a scan error merely because its path was excluded. The existing incomplete-note channel and `scanIncomplete` guard in core are the starting point, but the scope summary must be its own structured field; merely adding one prose note is not enough for auditability.

## Pull-request checks

Compute **effective scan scope for the head snapshot** before PR change extraction, and apply the same scope to base and head for comparison. Do not let a base-side config silently hide a change that the head includes, or vice versa: if config changes in the PR, disclose the old and new digests and the added/removed excluded roots, and mark the diff interpretation incomplete until it can be compared safely. The PR files list and diff must still inspect changed paths under excluded roots enough to count and disclose them; skipping event trigger detection entirely would make a fixture-only PR look like "nothing happened" without a check. If a supported manifest/lockfile or source path in the PR lies under an excluded root, the check says how many changed paths were excluded (bounded examples), and never treats them as an analysed dependency change. A source-only PR touching an excluded file may produce no verdict, but the check must still show its scope and omitted-change note.

If changed-file listing or diff parsing is truncated, fall back to the existing conservative full-scan path and report both the PR limitation and effective exclusions. A removed-last-usage verdict cannot be produced from removed lines that were excluded on either side or could not be read. For a declaration outside the excluded root, an excluded source line can still have been its last use, so reference completeness must be capped as above. Do not let head-only filtering turn a removed dependency into an apparently untouched package. The same scope digest must participate in the App's same-SHA analysis cache key; a re-run with changed config cannot reuse an old check.

## Verification and rollout gates

1. Lead rulings are recorded above: exact fixture roots only for v1, committed repo-root `.ghostdeps.json` with visible per-run CLI/Action override, and always-neutral checks when excluded manifests omit declarations. This accepted design authorises no implementation on its own. Specify the field schema and input syntax in reviewed implementation slices.
2. Core schema and presenters land together: scanner/handle scope, structured counts and completeness, engine notes/caps, CLI human/JSON, GitHub Check and Action output. A core-only implementation is not complete if human output can still look quiet. Keep any changed serialized contract versioned and deterministic.
3. Fixtures cover exact component matching, monorepo roots, zero and multiple matches, overlaps, a root containing a manifest and another containing only source, all-manifests-excluded, malformed manifests, limits while counting, config changed in a PR, excluded source-only PR, missing diff, and a dependency referenced across project boundaries. Assert both presenters show scope even with no verdicts and `--severity`/`--fail-on` cannot erase it.
4. Abuse fixtures cover traversal, symlinks, giant/hostile config text, ANSI/bidi and Markdown injection, many matched roots, unreadable paths and an adapter trying to read a filtered file. Check that errors degrade to incomplete or fail, never quiet success. Dogfood on #354's fixture case only after the contract and tests pass; do not patch the action or repo config first.

## Evidence and alternatives

The research lane's 25 September 2026 evidence memo for [#354](https://github.com/rowkavdev/ghostdeps/issues/354) compared [Knip's configuration](https://knip.dev/reference/configuration), [depcheck's ignore options](https://github.com/depcheck/depcheck/blob/main/README.md), [ESLint's ignore guide](https://eslint.org/docs/latest/use/configure/ignore), and [Git's ignore semantics](https://git-scm.com/docs/gitignore) and [per-path diagnostic](https://git-scm.com/docs/git-check-ignore). Knip distinguishes analysis-scope `entry`/`project` selection from issue suppression; depcheck separates path ignores from dependency-name matches; ESLint's global and local ignores have different traversal behaviour; gitignore has ordering, negation and parent-directory traps. Their normal output is not a proven complete exclusion ledger. The memo also cites historical [depcheck #190](https://github.com/depcheck/depcheck/issues/190) and [#331](https://github.com/depcheck/depcheck/issues/331) as examples of user confusion, not proof of a current defect. Its source links are research leads, not a contract for GhostDeps.

**General gitignore-style rules** would help scattered source exclusions, but add precedence, negation and audit complexity before the fixture problem needs them. **Dependency-name suppression** changes output, not analysis scope; it could hide findings while leaving omissions unexplained and is out of scope. **Always ignore `fixtures/`** is small but silent and risks skipping real projects with that name. **A presenter-only filter** hides the symptom after the engine already used those declarations; it cannot repair project counts or confidence. A visible, exact-root first slice is the smallest candidate that changes what is analysed while making that choice legible.
