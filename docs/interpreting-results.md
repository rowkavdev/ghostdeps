# Interpreting results

GhostDeps reports what it found in a repository snapshot. Read the evidence and limitations under a result before changing a dependency. A finding is not a command to remove a package. The GitHub App advises through a check; it does not block a merge. The CLI only gates a build if you explicitly set `--fail-on`.

## Verdicts and confidence

A **verdict** is a finding that suggests review of a dependency. It names the package, the rule that produced it, the evidence, a confidence level and any known limits. It is scoped to the project and files GhostDeps analysed, not every way a package might be used outside that snapshot.

| Kind                              | What it means                                                                                                                                                                                                  | Before changing anything                                                                                                                |
| --------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `unused`                          | GhostDeps found no use of a direct dependency after the adapter reported complete reference analysis. The PR-only `removed-last-usage` rule can report this when the last observed use was removed in that PR. | Check runtime loading, external consumers, scripts and conventions that static analysis might not understand. Removal is your decision. |
| `should-be-dev`                   | A runtime dependency was observed only in test, build or config paths.                                                                                                                                         | Check whether a published package or deployment still needs it at runtime. Moving it changes where consumers install it.                |
| `type-only`                       | Its observed imports are type-only and the analysed ecosystem strips types.                                                                                                                                    | Check the build and shipped output, not only source imports.                                                                            |
| `potentially-unnecessary`         | Evidence points to a possible native or existing alternative.                                                                                                                                                  | Compare behaviour, supported runtime versions and the APIs actually used. It is not an automatic replacement.                           |
| `duplicate-capability`            | More than one dependency appears to cover the same job.                                                                                                                                                        | Similar capabilities do not make APIs interchangeable. Choose with the project's needs in mind.                                         |
| `maintenance-risk` or `footprint` | A policy may call attention to maintenance or size.                                                                                                                                                            | Inspect the cited evidence. Size is not a removal verdict, and facts about a locked version do not prove the whole project is stale.    |

Not every kind is emitted by every adapter or enabled policy. A package not listed under Verdicts has **not** been certified safe or necessary. In a PR, GhostDeps generally scopes recommendations to dependencies that changed, with a special rule for a removed last use; it is not a fresh verdict on every dependency in the repository. A full scan and a PR scan answer different questions.

**Confidence** is how strongly the available evidence supports the particular finding: `high`, `medium` or `low`. It is not a percentage, an estimate of how much code can be deleted, or a promise that your tests will pass. High means the rule's evidence and coverage conditions were met; it does not prove the absence of runtime behaviour static analysis cannot see. Medium or low calls for more manual checking. Read the limitation text even on a high-confidence finding.

For example, `unused (high)` would mean that the rule saw no source import, script, config or convention reference, its adapter declared complete reference coverage, the relevant scan was complete, and the rule's other guards passed. It **does not** mean GhostDeps installed the project, ran tests, checked external users of a published package, or proved that deletion preserves behaviour. In the current build, `unused` confidence and severity are capped at **medium** pending 14 consecutive green nightly corpus runs. A note explains the cap. The example `unused (high)` describes the rule's possible meaning, not a result this build displays today.

Confidence and **severity** are separate. Severity is the level the CLI can use for `--fail-on`; it depends on the finding kind as well as confidence and is stamped by core. Do not infer a gate level from the displayed confidence. For an `unused` finding whose underlying evidence would be high, today's cap yields displayed confidence medium and severity medium, not high. `--fail-on medium` can catch it; `--fail-on high` cannot. The GitHub App's check remains advisory either way.

## Incomplete analysis and neutral checks

A GitHub Check with a `neutral` conclusion is **not** a clean bill of health and is not a GitHub Actions failure. It can mean there are verdicts worth reviewing, or that analysis was incomplete. Read the check title and Notes. "Analysis incomplete - see notes" means GhostDeps could not establish full coverage; "GhostDeps could not run" or "GhostDeps was busy" means the check could not give a normal answer. A `success` check means no significant issues were reported in the analysed scope, not that every dependency is needed. The GitHub App never uses `failure` as a dependency verdict.

Common reasons for an incomplete result include:

- A repository scan was truncated, or files were skipped because of size, depth, unreadability or safety limits. A malformed manifest can also leave declarations unknown.
- An adapter timed out, crashed, did not support a capability, or could not confirm that it checked scripts, config and other references. "No import found" is weaker than "unused" when those checks are missing.
- A PR diff or list of changed files could not be read fully; source-only PR checks can miss a removed-last-use finding when removed lines are unavailable. Read any fallback note to see whether the check widened to a full scan or skipped that check.
- A graph has no usable lockfile or is only partial. A transitive count can then be unknown or a lower bound, not zero. An impact calculation can hit a work limit without invalidating the separate dependency verdict.
- A policy or bounded analysis stage failed, or a cap prevented complete input from reaching the rule. Missing metadata can also leave optional package facts absent, but that absence alone is not an incomplete scan.

The response depends on the note. Fix malformed input or an unreadable file and rerun. For a timeout or size cap, reduce the scope or inspect the affected dependency manually; a repeat run may help a transient failure but cannot make unsupported analysis complete. Supply a supported lockfile if you need exact graph-based impact. If the note says scripts/config were not checked, search them yourself before removing the package. For an App failure or busy result, rerun the check or push a new commit when the service is available. Do not read missing findings as a reason to delete anything.

## Notes, awareness and package facts

**Notes** explain missing coverage or other context about a run. An incomplete note can make an otherwise finding-free check neutral; it does not itself recommend removal. Some notes are non-capping, such as an adapter's extra context or an impact work-limit note. An **awareness** item points out a relationship such as cross-ecosystem capability overlap; it makes no change recommendation and does not gate or alter the check conclusion. These are not verdicts.

**Package facts** are source-backed observations, not verdicts. When metadata is enabled and the exact locked direct dependency has one unambiguous version and registry origin, core can record that a registry marks it deprecated, that its repository host says it is archived, or the publication date of the **locked version**. An old locked version does not say the project has stopped releasing. No date here proves a newer version exists, and absent or false flags do not certify a healthy package. Facts have a source basis and declaring manifest identity in the result. They do not affect check conclusions, finding counts, CLI `--fail-on` or hidden counts. The CLI human output and the GitHub Check summary list them in a dedicated "Package facts" section (#385) with their source basis and declaring manifest; the JSON result carries the same structured fields. Metadata may be disabled or unavailable, especially in an offline CLI scan, so no fact is not a positive health finding.

**Impact** is another fact, read from lockfile graphs. "At least" means a lower bound, and "unknown" does not mean zero. Install footprint is approximate and may omit unsized packages. Neither number changes a verdict or check conclusion. See [Transitive impact](transitive-impact.md) for the exact counting rules.

## Why GhostDeps sometimes says less

The repository and its dependencies are untrusted input. GhostDeps parses source, manifests and lockfiles but does not install dependencies, run build scripts or execute the repository's tests during analysis. It will not evaluate an executable manifest to learn what it declares, or fetch packages to invent a graph when the lockfile is missing. Parsers and scans have limits so one hostile or enormous input cannot take over the analysis service. Adapters do not make their own network requests. These choices protect the service and keep a missing fact from becoming a confident false claim.

That means some questions remain unanswered: a dynamic import can be hard to trace, a package-manager resolution may be unknown without a lockfile, and a test outcome is not available from the analysis. GhostDeps reports a limitation, lowers confidence, or withholds the verdict rather than filling in a guess. A future fix-verification feature would require a separately approved isolation tier; today's scan is static-only. For the technical policy, see [ADR 0004](adr/0004-analysis-sandboxing.md), the [recommendation rules](recommendation-policy.md) and the [security model](security-model.md).
