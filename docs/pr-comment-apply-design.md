# PR comment and tick-to-apply design (#62)

- Status: Accepted design (architecture-lead verdict on [#387](https://github.com/rowkavdev/ghostdeps/pull/387), 2026-09-25); delivery remains gated as described below
- Date: 2026-09-25
- Scope: Human-in-the-loop removal on an existing PR branch, not automatic remediation or merging

Rowan proposed the PR comment and maintainer-ticked commit flow at 21:11 BST on 2026-09-25, then explicitly directed work on that goal at 21:12 BST. The architecture lead accepted this App/Action design on [#387](https://github.com/rowkavdev/ghostdeps/pull/387) after review. Acceptance of this delivery design does **not** flip [ADR 0005](adr/0005-fix-generation-and-verification.md) to Accepted. The architecture lead permits only an inert, diff-only core eligibility/preview slice while ADR 0005 is Proposed, as a sequencing interpretation of Rowan's goal directive, **not** an owner waiver of ADR acceptance. User-facing comment and apply rollout still waits for that ADR's Accepted flip and the slice-2 evidence gates.

## Decision

Use the App for analysis, one maintained PR comment, edit-event validation and dispatch. **Run the edit and lockfile regeneration in an explicitly installed, trusted workflow on the repository's runner**, not in the App worker. The App never executes repository code or edits the PR branch. An eligible maintainer ticks a box, and the workflow makes at most one commit for the checked batch after fresh validation. This is a separate, opt-in application path under [ADR 0005](adr/0005-fix-generation-and-verification.md), not a replacement for its dry-run CLI-first gate. Its earlier App-created _separate remediation PR_ is not this feature: that later mode needs its own approval and branch/permission design. The new mode modifies the existing PR head, with its author's review still required for merge.

Do not ship apply until the fix-eligibility evidence, bounded declarative edits, static overlay validation, supported lockfile regeneration, and reviewer gates in ADR 0005 have landed. A displayed finding or successful Check is insufficient. The first candidate slice is one supported JS/TS `package.json` + npm `package-lock.json` layout, with an explicit npm version and runner capability test; reject pnpm/yarn/workspaces, absent or ambiguous lockfiles, non-registry specs, unsupported fields, incomplete scans and uncertain edits until separately tested. Eligibility for `unused`, `should-be-dev`, and `type-only` follows ADR 0005's independent guards. Other findings, including native alternatives and overlapping capabilities, receive explanation only, with no checkbox. A finding's grouping and severity come from the **same `AnalysisResult`** that renders its Check through `@ghostdeps/checks-renderer`; the App must not reclassify it.

### Why not commit from the App?

A direct App `contents: write` edit seems smaller: no consumer workflow and a simple API commit. It fails if `package.json` is changed without the matching regenerated lockfile. Running `npm`/`pnpm` inside the service violates [ADR 0004](adr/0004-analysis-sandboxing.md); a hand-written lockfile rewrite is only acceptable after a format/version-specific deterministic, data-only writer proves consistency as ADR 0005 requires. That may eventually support a narrow direct-commit mode, but not a broad first release. This design instead limits App `contents: write` to triggering `repository_dispatch` on the base repository. The runner owns manifest and lockfile changes, then pushes one commit. `workflow_dispatch` may require `actions: write` and is not the proposed trigger. No `pull_requests: write` is required merely to comment or dispatch.

The runner is **the user's security boundary**, not an assertion that dependency installation is inherently safe. Use a trusted default-branch workflow, a pinned GhostDeps Action/version and pinned Node/npm, a fresh GitHub-hosted runner by default, explicit limits and concurrency, `persist-credentials: false`, and no token, App key, secrets or write credential in the checkout or npm process. Use lockfile-only regeneration with scripts disabled, no audit/fund and controlled registry/network configuration; package-manager config, plugins, registries and lifecycle behaviour still need adversarial review. Untrusted PR scripts are never run as a verification shortcut. Only after the runner validates the final bytes should a short-lived, repository-scoped **dedicated GitHub App installation token (not the workflow `GITHUB_TOKEN`)** be minted inside a separate commit-only job. That job consumes only verified, hash-bound bytes, with no checkout or package manager step. Keep its App private key in trusted repository/org Actions secrets, never in the PR checkout or analysis job; do not reuse the GhostDeps service App key. An installation that cannot safely configure this credential stays diff-only. Never run the PR's workflow file or arbitrary PR scripts with that credential. If the chosen npm invocation requires uncontrolled network, private registry secrets or unsupported configuration, refuse rather than leave a stale lockfile. This workflow is opt-in and consumes repository Actions minutes.

## State and event protocol

1. The normal PR scan pins the exact head SHA, effective scan-scope digest and policy/recipe versions. It completes the Check and renders one comment from that same result in the worker. The comment has a versioned hidden marker identifying the App/repository/PR, scan SHA and a bounded list of opaque deterministic finding keys (rule, ecosystem, project, manifest path, declaration kind/name, evidence digest and SHA). The marker is a locator, **not** a secret or an authority token. Render an ordinary explanation and limitations beside each finding; only independently eligible items receive `- [ ]` lines. Ineligible items explain why. A scan with user exclusions or incomplete reference evidence cannot silently offer removals; apply requires complete relevant scope per ADR 0005 and the [scan-scope design](scan-scope-design.md). Escape and cap all repository-controlled text.
2. List issue comments with bounded pagination and identify our own author and marker. Create only if absent; update the same comment by ID when the canonical output changes; an identical render is a no-op. Multiple matching bot comments are an ambiguity to repair explicitly, not an invitation to choose one and apply. Use a per-PR serialisation key and re-read before create/update to avoid duplicates and event races. Existing same-SHA cache stores the rendered Check, not authority or current tick state. It may help render, but can never substitute for current PR, comment, permissions and eligibility reads.
3. Add `issue_comment` to the manifest and an explicit `edited`-only handler (plus the existing default-deny filter). At event time verify signature, repo/installation, open PR identity (not an ordinary issue), exact bot-owned comment ID and marker, actor's current repository permission through the GitHub API, and an allowed association (`OWNER`, `MEMBER`, `COLLABORATOR`). Neither association nor the GitHub checkbox UI is sufficient alone. Reject non-maintainers, suspended installations and failed permission checks. A non-maintainer edit is ignored for apply and the comment is restored to the canonical unticked state. Do not infer authorisation from the comment's `updated_at` or its author; the _editor_ in the signed delivery is the actor. For races, re-read the comment and PR immediately before dispatch; stale delivery or overwritten edit refuses.
4. `changes.body.from` to current body must differ **only** in exact `[ ]` to `[x]` checkbox tokens for present eligible finding keys; no added lines, changed hidden fields, unchecked entries, changed explanation or reordered content. Parse bounded bytes/lines and a fixed grammar, compare the non-checkbox bytes to a freshly generated canonical rendering for the pinned result, reject duplicate/missing keys, malformed markdown, forged markers and over-large edits. A change that includes anything else restores the canonical body without dispatch. Never execute or evaluate comment text. A valid batch is all currently newly ticked eligible keys, not a partial or arbitrary string search.
5. Re-fetch PR head, scan provenance and the complete current comment. If the head differs from the scan SHA, refuse, write a brief stale/re-scan note in the maintained comment and queue a new analysis; never reuse the old proposed patch. If the comment has moved, the repo/config or relevant scan scope is incomplete, or any finding's evidence/eligibility cannot be verified, refuse the whole batch. An unavailable Action or write permission leaves a diff-only explanation with disabled checkbox presentation. Failure and refusal should not masquerade as applied.
6. Dispatch a **short-lived signed apply envelope** that binds installation/repository ID, PR number, base and head identities, comment ID, canonical body digest, selected finding keys and evidence digests, scan-scope digest, issue-comment delivery ID, expiry and a nonce. Sign with an App-held dedicated key; pin the public verification key in the trusted Action version with a rotation plan. The dispatch payload is untrusted until verified. The runner verifies signature, expiry, recipient and exact known signer, then independently reads the PR, comment and scan provenance again. It parses current tick state, not the payload as a substitute. It re-runs full static analysis and fix eligibility against the pinned PR head and compares exact keys/evidence. Webhook dedupe and `concurrency` keyed by repo/PR prevent parallel batches; a repeated envelope is a no-op if the head moved or matching commit already exists. No persistent finding/tick store exists: the comment is canonical state. Delivery IDs and signed nonces are transient replay guards, not a second source of tick truth.
7. Generate minimal declarative edits at exact manifest paths using ADR 0005's expected hashes and guards. Regenerate the matching lockfile on the runner; require a coherent manifest/lockfile pair, inspect the diff and reject any unrelated file/dependency/registry or resolution change beyond the enumerated recipe. Run static overlay re-analysis; a failed or incomplete analysis blocks. Re-read remote head immediately before write and commit by compare-and-swap to the verified old SHA (no force push), with one commit containing the entire selected batch. If GitHub's API cannot atomically enforce the expected ref, reject races and never overwrite another writer. The commit must use the **consumer's dedicated App bot identity**, whose installation token performed the write, not `ghostdeps[bot]` and not the maintainer's personal identity. Do not override the API author/committer to impersonate either one. The commit message cites the rule and finding keys and notes the human-triggered batch. No auto-merge.
8. After the commit, do **not assume CI ran**. A push with a workflow `GITHUB_TOKEN` does not normally trigger new workflow runs. The commit-only job therefore uses the dedicated App token above; GitHub documents that GitHub App installation-token pushes can trigger normal `push` and `pull_request` workflows ([triggering a workflow](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow)). Before calling the batch applied, verify on a live test repository that this exact token/ref/API commit path triggers the expected PR CI and an App synchronize scan. After each production write, poll boundedly or subscribe for the expected checks at the **new SHA** and confirm the fresh GhostDeps analysis and the repository's required CI checks/workflows (resolved from current branch protection and expected workflows) were actually created. A repository with no reliably discoverable CI requirement is not described as CI-verified; the comment records what ran and what did not. If any expected run is absent, skipped, queued for approval, failed, or times out, keep the maintained comment in a visible `commit made; verification pending/failed` state and do not claim clean status or auto-merge. The fresh scan updates the **same** comment and removes resolved boxes only after re-evaluating the new head. On failure or ambiguity it re-renders an accurate refusal/status on the same comment, retaining only verified current-head tick intent if safe; never claim a fix. A crash after commit but before comment update is recovered by checking branch head/commit before any retry, not by blindly committing again.

The envelope is a command authentication mechanism, **not** a side-channel state store. Its signer key must stay outside PR code and logs. Treat public comment text and repository content as adversarial. Never turn a marker, check state, association label, dispatch event or a green CI run into a grant to write.

## Forks and permissions

An eligible fork PR requires `maintainer_can_modify === true` **at apply time** and an actually verified write path to that **fork branch**. The commit would land in the contributor's fork, not the base branch; say this plainly in the comment and confirmation copy. A base repository workflow's `GITHUB_TOKEN` is not assumed to write to an arbitrary fork. Nor does the allow-edits flag by itself prove that an App installation token or Actions credential can push there. Before enabling fork apply, integration-test the precise token, endpoint, installation scope, protected-branch rules and branch policy on a real same-owner fork and unrelated-owner fork. If any permission or safe credential is unavailable, disable the checkbox and show diff-only instructions. Never ask a contributor to expose a fork token to an untrusted workflow. The first rollout may therefore be **same-repository PRs only**; fork apply is explicitly gated, not implied to work.

Permission delta for opt-in App installs: `issues: write` to create/edit the single issue comment, `contents: write` to create `repository_dispatch` against the base repository, existing `pull_requests: read` for PR identity/allow-edits/head, existing `checks: write` for Checks, and mandatory `metadata: read`. Avoid `pull_requests: write`, `actions: write`, organisation-wide permissions and using the App content-write token inside analysis workers. Mint narrow tokens only at the dispatch boundary; App checkout/analysis retains `contents: read` and `checks: write`. The workflow `GITHUB_TOKEN` is read-only in both jobs. The separate commit-only job mints a short-lived, single-repository dedicated GitHub App token with `contents: write` for the final API commit and the minimum `issues: read` / `pull_requests: read` needed to revalidate PR/comment state; the analysis job has no write credential. The trusted default-branch workflow holds the dedicated App ID/private key as Actions secrets, only exposed to the commit job, and never passes them into a PR checkout or package-manager process. Artifact transfer between jobs is itself untrusted: the commit job verifies signed envelope, pinned old SHA, content hashes, changed-path allowlist and current PR/comment state before the API write. A push made with the repository `GITHUB_TOKEN` is prohibited, even if the commit succeeds, because it can suppress the new-head CI; see [GitHub's event recursion rules](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow). GitHub installations must approve increased permissions again. Keep the scan-only experience functional for installations that decline. Change `packages/github-app/app.yml`, `docs/github-app.md`, manifest parity tests and **`docs/security-model.md` in the same permission-change slice**. In that security update justify every new permission, dispatch/token isolation, untrusted payload, fork limitation and runner risk line by line. Update ADR 0003's current-state statements or link an explicit superseding decision once accepted, without pretending the old read-only version is still current.

## Slices and acceptance

1. **Design gate (met on #387):** reviewer-1 checked the proposal and the architecture lead accepted the App/Action boundary, first ecosystem, same-repo-first fork policy and signed envelope/consumer-App commit model. ADR 0005 remains Proposed; its Accepted flip is a separate owner decision.
2. **Core eligibility/preview (inert, diff-only while ADR 0005 is Proposed):** ADR 0005's versioned finding key, independent `FixEligibilityEvidence`, exact declarative edit validation, static re-analysis, supported npm manifest/lockfile consistency and dry-run CLI, with corpus/adversarial fixtures. No comment and no write permission.
3. **Comment-only App (gated on ADR 0005 Accepted and slice-2 evidence):** same-result renderer, one-comment discovery/update, bounded parser, editor permission checks, stale re-scan and refusal behaviour. Permission/manifest/docs/security changes land together and reapproval is documented. No dispatch until safe workflow available.
4. **Opt-in same-repo apply Action (gated on ADR 0005 Accepted and slice-2 evidence):** signed dispatch, trusted default-branch runner, pinned toolchain, head compare-and-swap, lockfile regeneration and one-commit batch. Dedicated tests for replay, crashes and every refusal path. Fork mode remains disabled until its separate live capability and security gate passes.
5. **Fork gate and other ecosystems:** prove the exact cross-fork write path or keep diff-only. Add pnpm/yarn and other ecosystems only with package-manager-specific lockfile, workspace and runner threat tests.

Test matrix: issue-comment edited webhook fixtures (valid tick, non-maintainer, bot, forged marker, body text change, uncheck, duplicate keys, stale head, deleted PR, permission revoked); association and live-permission matrix; one-comment idempotence across duplicate/out-of-order deliveries and same-SHA cache; comment tampering/control text and huge input; two editors ticking concurrently; missing workflow/installation reapproval; same-repo branch protection; fork allow-edits on/off and missing fork token; dispatch forgery/replay/expiry; malicious npm configuration and scripts; lockfile mismatch, unexpected transitive resolution, runner crash after push, a `GITHUB_TOKEN`-authored push that suppresses CI, and a missing/new-head delayed check. Assert **zero writes on every pre-commit failure**, explicit pending/failed new-head status on post-commit failures, no stale lockfile commit, no token in logs/workspace, and one successful commit for a valid batch. Document Actions minutes and that runner-based install does not validate runtime behaviour.
